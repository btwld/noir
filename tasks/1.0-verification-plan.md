# Core-Framework 1.0 Verification Plan

Purpose: a standing, repeatable protocol that lets anyone (human or agent, on a
fresh checkout) confirm that the implementation matches what the trackers
claim, without relying on any workspace-scratch evidence. All process
artifacts formerly cited under `.context/` were ephemeral; **the only durable
evidence is the committed code, the committed test suite, and git history.**
This plan re-derives the 1.0-readiness claim from those alone.

## 1. What "1.0" means here

Per `CLAUDE.md`/`AGENTS.md`, core-framework 1.0 is a **scope boundary**, not a
release: the declarative Widget/Element/RenderObject lifecycle, state, layout
and paint recording, text, focus and input, inherited dependencies, animation,
bundled native loading, and the documented widget/low-level APIs. It does
**not** claim pub.dev publication, a stable version/tag, platform runtime
acceptance, or resolution of the documented read-only OpenTUI limitations.
The package version is `0.1.0-dev.1`.

## 2. Fresh-checkout verification protocol (all automated)

Run from the repository root. Expected results for the current verification
tree on 2026-08-03; §3 retains the historical `d24a1fd` spot-audit baseline.

```bash
# 0. Setup (required once per checkout)
git submodule update --init external/opentui
dart pub get

# 1. Native artifacts match the pinned manifest (6/6)
dart run scripts/fetch_opentui_binaries.dart --verify-only

# 2. Formatting and static analysis (0 changes, 0 issues)
dart format --output=none --set-exit-if-changed lib/ test/ example/ bin/ scripts/
dart analyze --fatal-infos

# 3. Architecture fitness functions (168 pass) — these enforce the layer
#    invariant: Widgets declare / Elements preserve identity / RenderObjects
#    layout+paint / Compositor talks to OpenTUI / native layer owns FFI.
dart test test/architecture/

# 4. Full ordinary suite (1175 pass, 2 skipped)
dart test --exclude-tags process-spawning --concurrency=1

# 5. Separately selected health check
dart test test/bin/health_check_test.dart --concurrency=1

# 6. Primitive rendering parity vs. the Go reference implementation
GO_SNAPSHOT_CMD=./scripts/run_go_snapshot.sh dart test -r expanded test/parity/primitives_parity_test.dart --concurrency=1

# 7. Widget rendering parity vs. the Go reference implementation
GO_SNAPSHOT_CMD=./scripts/run_go_snapshot.sh dart test -r expanded test/parity/widget_parity_test.dart --concurrency=1

# 8. Package hygiene (0 warnings)
dart pub publish --dry-run
```

Do not replace the explicit parity selectors with the whole `test/parity/`
directory. That directory also selects `go_snapshot_wrapper_test.dart`, whose
signal, process-group, and forced-termination lifecycle checks require exact
task-specific authorization.

Any deviation from the expected results is a regression against the audited
baseline and must be triaged before any 1.0 claim.

## 3. Claim-vs-code spot audit (anti-hallucination check)

Performed 2026-08-03 against `d24a1fd`: 15 tasks marked `committed` in
`tasks/phase-9-post-v1-reference-review.md` were sampled, favoring concrete
falsifiable claims (deleted symbols, `@internal` markers, exact method
counts, enum values, consumer lists). **15/15 verified true in the tree.**
A consumer-readiness audit the same day found every README/example API real
and the muse→noir rename fully clean.

To repeat this audit: sample ≥10 `committed` rows from the Phase 9 finding
ledger, and for each, verify its specific claim directly in `lib/`/`test/`
(grep for deleted symbols, read the cited files, run the cited test files).
The ledger's process narrative (RED/GREEN transcripts, mutation counts,
verifier verdicts) is historical and not re-checkable; only code-level claims
are auditable.

## 4. What automated verification does not establish

| Gap | Current limitation | Resolution boundary |
| --- | --- | --- |
| Real-terminal visual behavior (true color, cursor escapes, glyphs) | Goldens capture characters plus style/cursor sidecars, not terminal escape rendering. A host-specific iTerm run can confirm or reproduce behavior, but it cannot resolve known P9-018 or P9-020–P9-023 limitations. | Repeat the documented dedicated-window iTerm workflow only with explicit authorization and retain release evidence through an intentionally durable channel. |
| Linux/Windows runtime | Local evidence is macOS-only and GitHub Actions is intentionally disabled. | Enable/dispatch CI once with explicit authorization, or run the suite on those hosts manually. |
| Decorated viewport destination clipping | Decorated `drawBox` content can escape a `ScrollBox` viewport (P9-018); failure-atomic, command-complete scissoring requires the guarded native status contract represented by P9-005N/P9-018. | A separate dependency-strategy decision is required to change the pinned OpenTUI source, ABI, and artifacts. |
| Complex grapheme rendering and editing | Exact terminal-cell width (P9-020), packed EGC paint/storage (P9-021), native-cell selection mapping (P9-022), and preferred vertical caret-column behavior (P9-023) remain unavailable; visible effects include cluster loss and caret misalignment. | A separate dependency-strategy decision is required; another partial Dart approximation must not be described as correctness. |
| High-level startup input/capability-query ordering | Current `TerminalSession` invokes `Renderer.setupTerminal()` before `StdinInputDriver.start()`, leaving capability replies able to race input acquisition. The raw bindings example directly demonstrated the canonical/echo mechanism. The high-level captures were clean and high-level corruption was not reproduced, so that visible high-level effect remains an inference rather than a claimed reproduction. | P9-086 is unresolved `required-local` work and blocks Noir-local Phase 9 closeout. It requires its own full implementation workflow and authorized dedicated-terminal acceptance; optional P9-039 evidence does not own the correction, and P9-085 remains the separate pinned-native cursor-restoration limitation. |
| Alternate-screen main-screen/cursor restoration | On the observed macOS/iTerm run, pinned native capability probes moved the main-screen cursor before alternate-screen entry, so shutdown returned to row 1/column 1 instead of the launch cursor and overwrote prior rows (P9-085). Clean in-app frames, a usable shell, and `stty` equality do not establish cursor-position or content restoration. | A separate dependency-strategy decision is required to change the pinned native source and rebuild the bundled artifacts; Dart-side ANSI/save-slot workarounds would duplicate native terminal ownership. |
| PTY/terminal-mode behavior outside the parser | `createTuiTestApp` feeds the production parser but is not an OS pseudo-TTY. | A future separately authorized PTY harness is required. |

Real-terminal evidence can characterize these effects on one host; it does not
close P9-018, P9-020 through P9-023, P9-085, or the required-local P9-086
startup-order task. Linux/Windows runtime and OS-PTY behavior also remain
outside the automated local claim.

## 5. Remaining steps to an actual 1.0 release (decision list)

1. Close P9-086 through its separate architect → TDD executor → independent
   verifier → local gates → authorized dedicated-terminal acceptance → commit
   workflow. It is `required-local`, not optional P9-039 evidence or the
   read-only-upstream P9-085 restoration limitation.
2. Decide the version story: `0.1.0-dev.1` → stabilization releases → `1.0.0`
   (CHANGELOG + tag). The Noir-local closeout program does not prevent choosing
   a version, but the user-visible §4 limitations are release risks to accept
   explicitly.
3. Decide whether to publish to pub.dev (workflows exist but are dormant by
   policy; `dart pub publish --dry-run` is clean).
4. Decide what release-candidate evidence to retain or repeat: macOS
   real-terminal visuals and, if desired, Linux/Windows runtime. Such evidence
   can characterize the limitations; it cannot resolve P9-018 or P9-020
   through P9-023, and it cannot by itself repair the P9-085 main-screen and
   launch cursor restoration defect.
5. Accept or re-scope the retained `read-only-upstream` program recorded in the
   Phase 9 tracker. Release-facing risks include native failure reporting
   (P9-005N), decorated viewport destination clipping (P9-018), and complex-
   grapheme width/paint/selection/caret behavior (P9-020, P9-021, P9-022, and
   P9-023), plus alternate-screen main-screen content and launch cursor
   restoration (P9-085). Clipping, Unicode behavior, and P9-085 restoration
   are user-visible runtime risks.
