# Noir 1.0 release and `main` handoff plan

This is the ordered execution plan for moving the reviewed alpha candidate from
private preparation to `1.0.0-alpha.1`, `1.0.0-beta.1`, and stable `1.0.0`.
It supplements [release readiness](release-readiness.md), which records the
current evidence and open risk.

## Fixed decisions and boundaries

- `leoafarias/noir` is the intended repository and remains private during
  preparation.
- Public history will start clean on `main`. The current private history is
  preparation and recovery material, not the intended public history.
- The OpenTUI submodule remains read-only and pinned at
  `ddbc9edf81a1fa89961135ab0481df15054ed4b0` unless a separate dependency
  decision explicitly changes that boundary.
- Do not patch OpenTUI, advance its gitlink, push OpenTUI refs, run its
  workflows, or add a Noir-owned ANSI workaround for its cursor-restoration
  limitation.
- GitHub Actions stay disabled until separately authorized.
- Native rebuilds, artifact replacement, real terminal/PTY execution, tags,
  releases, repository visibility changes, and publication each require their
  own explicit authorization.
- Stable publication must pause until the release owner declares the beta soak
  sufficient. No implementation task may invent a soak duration or threshold.

## Phase 1: preserve private preparation

1. Commit the reviewed alpha candidate on a private preparation branch.
2. Create and verify an offline Git bundle containing every preparation commit
   before rewriting or replacing public-facing history.
3. Record the preparation commit SHA, tree SHA, archive inventory, archive
   SHA-256, six native hashes, tool versions, and dated verification outputs.
4. Keep `pubspec.lock` untracked because Noir is a package, not an application.
5. Keep `.conductor/settings.toml` checked in so a fresh workspace performs a
   noninteractive submodule initialization and `dart pub get`.
6. Scan the entire retained history for secrets and stale repository, branch,
   PR, tag, and release references.

Exit criteria:

- the preparation branch is clean and recoverable;
- its commit is pushed privately;
- the recovery bundle has been cloned or verified with `git bundle verify`;
- the pinned OpenTUI gitlink and all native artifacts are unchanged.

## Phase 2: rebuild and own native artifacts

This phase is blocked until an exact native-build authorization is granted.

1. Check out the pinned OpenTUI source in two clean, differently located build
   roots. Verify the source is clean before and after each build.
2. Use one reviewed Noir-owned build wrapper, Zig 0.14.1, and these explicit
   targets:

   - `x86_64-linux`
   - `aarch64-linux`
   - `x86_64-macos`
   - `aarch64-macos`
   - `x86_64-windows`
   - `aarch64-windows`

3. Build every target in both roots. Remove or remap build paths and require
   byte-identical output between roots.
4. Scan all artifacts for absolute build paths, debug paths, and unexpected
   metadata.
5. Record the OpenTUI source commit, Noir build-recipe commit and digest,
   Zig/toolchain version, runner image digest, exact commands, target triples,
   build timestamps or run IDs, attestations, and both SHA-256 tables.
6. Verify file formats, architectures, all required exports, ABI version 2,
   the macOS 15.0 deployment floor, manifest integrity, and packaged health
   checks. Any ABI, header, or generated-binding change is a stop condition.
7. Host immutable recovery bytes in Noir, not the OpenTUI fork. For clean
   public history:

   - root commit A contains the six rebuilt binaries and provenance;
   - package commit B adds the reviewed source and points manifest recovery
     URLs to commit A by full SHA.

8. Update Noir's manifest, fetch tool, tests, and notices for the new
   Noir-owned URLs and hashes without changing the OpenTUI gitlink.
9. After visibility changes, require anonymous downloads of all six manifest
   URLs to reproduce the recorded hashes.

Reuse the approved bytes for beta and stable unless the pinned native source or
ABI changes. Do not rebuild only because the Dart package version changes.

## Phase 3: establish clean `main`

1. While the GitHub repository remains private, create clean root commit A and
   package commit B as described above.
2. Before pushing, replace every `/blob/master/` URL, CI branch filter, branch
   assertion, and other default-branch reference with `main`.
3. Run the full verification matrix against the exact package commit.
4. Push `main` without force, set it as GitHub's default branch, and refresh
   local `origin/HEAD`.
5. Keep `master` temporarily as private rollback material until the fresh
   workspace preflight passes.
6. Import `git@github.com:leoafarias/noir.git` as its own Conductor project.
   Do not reuse a workspace whose project root or default-branch environment
   still belongs to another repository.
7. Create a fresh workspace from the remote default branch and record:

       CONDUCTOR_ROOT_PATH resolves to Noir
       CONDUCTOR_DEFAULT_BRANCH=main
       origin is git@github.com:leoafarias/noir.git
       origin/HEAD -> origin/main
       workspace HEAD == origin/main at creation
       git status --porcelain is empty after setup
       external/opentui is clean at ddbc9edf81a1fa89961135ab0481df15054ed4b0

8. Have a fresh reviewer inspect the complete diff and run the standard gates
   from that workspace.
9. Delete remote `master` only after the preflight succeeds, clean public
   history is still the selected policy, and deletion is explicitly approved.

## Phase 4: release `1.0.0-alpha.1`

Freeze one clean commit and retain its commit SHA, tree SHA, archive inventory
and hash, native hashes, tool versions, and dated gate outputs.

Required gates on that exact commit:

- formatting and `dart analyze --fatal-infos`;
- architecture tests and the ordinary suite excluding
  `restricted-process-lifecycle`;
- focused Dart-versus-Go parity checks;
- native manifest, URL, export, architecture, ABI, and macOS-floor checks;
- lower-bound dependency resolution;
- dartdoc link validation, Pana, actionlint, and ShellCheck;
- publish dry-run with zero warnings and an intentional archive inventory;
- packaged health check and CLI bundle;
- a clean downstream package consumer;
- fresh Conductor `origin/main` evidence;
- anonymous repository, issue, README, notice, and native URL checks;
- clean status, `git diff --check`, secret scan, and history scan.

Release sequence:

1. Obtain explicit approval to make the repository public. Immediately install
   no-force/no-delete protection on `main` and immutable `v*` tag rules.
2. Enable Actions only with explicit approval.
3. Configure protected `pub.dev` and `github-release` environments. The Dart
   publisher must use `environment: pub.dev`; final GitHub release creation
   must wait on `github-release`.
4. Create and push a signed, annotated `v1.0.0-alpha.1` tag.
5. Let tag preflight and packaged-release verification run, but do not approve
   automated publication: pub.dev requires the package's first version to be
   published manually.
6. From a fresh detached checkout of the exact signed tag, obtain separate
   publication approval and run `dart pub publish`.
7. Verify the pub.dev API, version, archive, archive SHA-256, inventory, and
   package links. Cancel the waiting alpha automated-publish job.
8. Configure trusted publishing for `leoafarias/noir` with tag pattern
   `v{{version}}` and the protected `pub.dev` environment.
9. Approve the GitHub-release job and verify its prerelease status, tag, and
   attached checksum/provenance archive.

Alpha is an integration preview. It does not claim production stability, a
full six-architecture runtime matrix, or real-terminal lifecycle acceptance.

## Phase 5: release `1.0.0-beta.1`

1. Start from a fresh branch and workspace based exactly on `origin/main`.
2. Close the designated beta findings:

   - grapheme-aware text width and painting;
   - trailing-newline layout;
   - text-editing grapheme boundaries;
   - TextArea cursor visibility after resize;
   - animation listener callback isolation;
   - native capability detection.

3. Bump every version surface to `1.0.0-beta.1`. CHANGELOG and architecture
   assertions must be cumulative and ordered: beta.1, then alpha.1.
4. Repeat every alpha gate plus packaged execution on all six supported
   OS/architecture targets. Assert both operating system and architecture;
   runner labels alone are not evidence.
5. Run real terminal, PTY, or ConPTY checks only after exact authorization.
   Record the pinned upstream cursor limitation if observed; do not patch it in
   Noir.
6. Create and push a signed `v1.0.0-beta.1` tag. Hold both pub.dev publication
   and GitHub release creation behind their protected environments.
7. After all verification paths pass, explicitly approve pub.dev publication,
   verify its audit-log link and archive, then approve the GitHub release.
8. Begin the beta soak. Only the release owner decides when it is sufficient.

## Phase 6: release `1.0.0`

1. Close or deliberately redesign the stable-contract findings:

   - immutable collection and value inputs;
   - decoration and `BoxShape` promises;
   - `DirectBufferAccess` lifetime and snapshot semantics;
   - exception-safe `PersistentUtf8Text` replacement;
   - scroll callback semantics.

2. Bump every version and install surface to `1.0.0`. CHANGELOG order becomes
   stable, beta.1, alpha.1, and README loses prerelease wording.
3. Produce and approve a public API diff against beta.
4. Repeat the full six-target execution, documentation, Pana, package,
   consumer, and provenance gates on the exact stable commit.
5. Preserve the cursor-restoration behavior as a documented upstream
   limitation with Noir cleanup tests passing. It is not by itself a stable
   blocker.
6. Hard pause before tagging until the release owner records that the beta soak
   is sufficient.
7. Create signed `v1.0.0`, approve trusted publication only after every held
   verification job passes, verify pub.dev and its audit/archive evidence, and
   then approve the GitHub release.

## Rollback and irreversible-operation rules

- Before every remote mutation, retain the commit SHA, tree SHA, archive hash,
  manifest hashes, evidence bundle, and a verified Git recovery bundle.
- Default-branch changes, Actions enablement, and environment settings are
  reversible while the repository remains private and untagged.
- History replacement, deleting `master`, native-byte replacement, public
  visibility, remote tags, GitHub releases, and pub.dev publication each need
  separate explicit approval.
- Public disclosure cannot truly be undone because clones and caches may
  persist.
- Never force-push `main`, move or reuse a pushed release tag, or overwrite a
  published version.
- A failed tagged candidate advances to the next prerelease version; it does
  not reuse the tag.
- Before publication, revert a bad native-refresh commit. After publication,
  retract a defective pub.dev version if necessary and issue a new version;
  deleting a GitHub release does not erase publication history.
