# Phase 2 native-build implementation contract

Status: design approved; implementation and candidate builds pending.

This contract refines Phase 2 of
[`1.0-release-plan.md`](1.0-release-plan.md). That plan remains authoritative
if the documents conflict. The release owner authorized the six native builds
described here, but did not authorize replacing tracked artifacts, changing
the ABI, generated bindings, native manifest, OpenTUI gitlink, or recovery
URLs, or performing any later release operation.

## Decision

Use a hybrid reproducibility design:

1. commit a reviewable Noir-owned build wrapper and immutable runner recipe;
2. execute that committed recipe in two clean, independently cached, and
   differently located OpenTUI roots;
3. retain unsigned SLSA-shaped provenance, build information, logs, scans, and
   two SHA-256 tables outside the tracked package;
4. save a checksummed local runner-image archive under the gitignored
   `.context/recovery/` directory.

The committed recipe and recorded input digests are the durable source of
truth. The local image archive is recovery material, not a release artifact or
a substitute for the recipe. No image or attestation is pushed in this phase.

The resulting matched binaries are candidates. A separate approval is needed
before any candidate replaces a file under `native/` or changes
`native_manifest.json`. Once separately approved and adopted, those exact
bytes are reused for beta and stable unless the pinned OpenTUI source or ABI
changes.

The runner uses Linux arm64 deliberately so one recorded environment produces
all six cross-targets. Its Dockerfile pins the platform-specific Debian base
manifest by digest, adds the checksum-verified official Zig archive, and
installs only the certificate, minisign, and LLVM inspection/stripping tools
required by the recipe from a dated Debian snapshot. The recipe also verifies
the archive's official detached signature, fetched from the archive URL plus
`.minisig`, against the pinned Zig minisign public key. The final image
configuration digest, base digest, snapshot timestamp, resolved package
inventory, tool versions, and both archive verification results are captured
in build information. Changing any of them creates a new recipe that must be
reviewed and committed before another build.

The runner seeds `zg` into its Zig package cache and verifies that Zig reports
the expected package hash. The actual builds run with networking disabled.
Neither the runner nor the wrapper edits the pinned OpenTUI checkout.

## Noir-owned files

Implementation is limited to these intended tracked surfaces:

- `scripts/build_opentui_candidates.dart`: guarded command-line entry point;
- `scripts/native_build/`: runner recipe and build, inspection, provenance,
  and safe-filesystem helpers;
- `test/scripts/native_build/`: focused contract tests;
- `tasks/`: this contract, implementation plan, and release-readiness links.

Candidate libraries, runner archives, logs, downloaded tool archives, caches,
and generated evidence remain under `.context/` and are never added to the
package. The wrapper has no install, manifest-update, upload, tag, release, or
publication mode.

The work is deliberately sequenced into auditable commits. This contract is
committed first. The tested wrapper and runner recipe form a second clean
commit and are pushed before any candidate build, so the recipe commit in
provenance already exists. Builds run only from that clean commit. A later
documentation commit may summarize verified hashes and evidence inventory,
but it does not add candidate binaries or generated evidence.

## Command contract

The entry point has two modes:

- `--plan` performs all repository, pin, tool, path, and recipe checks and
  prints the exact target matrix and container commands without building or
  writing candidate files.
- `--execute-native-build` performs the authorized build. The explicit flag is
  intentionally verbose so ordinary verification cannot start native builds
  accidentally.

Execution refuses to start unless all of the following are true:

- the repository root, origin URL, current committed recipe, and clean working
  tree match the preflight contract;
- `HEAD` contains the required preparation commit;
- the submodule checkout and recorded gitlink both equal the OpenTUI pin and
  its tracked and untracked status is clean;
- Docker is available without allocating a TTY or PTY;
- `.context/` is ignored by Git; and
- the requested run directory is either created by the wrapper or contains
  the wrapper's exact run marker.

Cleanup is restricted to marker-owned run directories. The wrapper never
recursively deletes a workspace, repository root, home directory, unresolved
path, or caller-supplied directory that lacks the marker.

## Reproducible build protocol

The wrapper performs these ordered operations:

1. Build the runner from the committed recipe, verify the image configuration
   digest and embedded tool versions, save it with `docker image save`, and
   record the archive's size and SHA-256 under `.context/recovery/`.
2. Clone the local read-only OpenTUI submodule with no hardlinks into two
   wrapper-owned roots. Check out the pin detached, verify `HEAD`, the tracked
   tree, and an empty status in each root, and normalize source mtimes to the
   pinned commit timestamp without changing content.
3. Mount both source roots read-only at visibly different container paths.
   Root A and root B also receive different output, local-cache, and
   global-cache paths. Each root receives an independent copy of the verified
   seed cache. The fixed source mount paths are
   `/build/noir-root-a/opentui` and `/opt/repro/noir-root-b/opentui`; cache and
   output paths retain the corresponding root marker so path scans can detect
   leakage.
4. Run the container with no network, no TTY, all capabilities dropped,
   `no-new-privileges`, a read-only root filesystem, a bounded temporary
   filesystem, a fixed hostname, `TZ=UTC`, a fixed `C.UTF-8` locale,
   `SOURCE_DATE_EPOCH` equal to the pinned source timestamp, and umask `022`.
5. Invoke the upstream `zig build` once per explicit target. Root A uses plan
   order and root B reverse order so cache and enumeration order cannot hide a
   dependency. Every invocation uses root-specific explicit `--prefix`,
   `--cache-dir`, and `--global-cache-dir` paths outside the read-only source.
6. Copy each raw output to a root-specific candidate area, canonicalize only
   the format-owned linker identity metadata described below, apply the same
   pinned `llvm-strip --discard-all` normalization, and retain both the raw and
   normalized SHA-256 values. This reviewed operation removes local and debug
   symbol records, including Mach-O `N_SO` and `N_OSO` path-bearing records,
   while preserving the defined external export set. If normalization removes
   a required export or does not eliminate a disallowed path, stop instead of
   altering OpenTUI or inventing another transformation.
7. Require normalized root-A and root-B artifacts to be byte-identical for all
   six targets. No artifact is selected when any pair differs.
8. Recheck both OpenTUI clones and the original submodule for the exact commit,
   tree, and clean status. Recheck the Noir worktree and all protected tracked
   paths before writing the final evidence statement.

Identifier canonicalization is deliberately narrow and happens before the
pinned LLVM rewrite:

- Mach-O: zero the single `LC_UUID` payload. LLVM then regenerates the arm64
  ad-hoc linker signature over canonical content.
- PE/COFF: zero the COFF timestamp and debug data-directory entry, then clear
  the exact `.buildid` raw payload. The PDB is not a candidate, so retaining a
  root-derived PDB association would be misleading.
- ELF: do not canonicalize identifier metadata.

The format parser fails closed on unexpected magic, architecture,
load-command or optional-header shape, missing or duplicate identity records,
invalid ranges, or a nonzero PE checksum. It never searches for or patches an
arbitrary byte pattern. Two-root proof must show byte equality after both
steps, retained exports and format/architecture, the macOS 15.0 floor, and a
valid regenerated arm64 ad-hoc signature.

The six build targets and expected library names are:

| Approved target | Exact Zig target query | Expected output |
| --- | --- | --- |
| `x86_64-linux` | `x86_64-linux` | `libopentui.so` |
| `aarch64-linux` | `aarch64-linux` | `libopentui.so` |
| `x86_64-macos` | `x86_64-macos.15.0` | `libopentui.dylib` |
| `aarch64-macos` | `aarch64-macos.15.0` | `libopentui.dylib` |
| `x86_64-windows` | `x86_64-windows` | `libopentui.dll` |
| `aarch64-windows` | `aarch64-windows` | `libopentui.dll` |

The output column names the candidate/package filename. The pinned Zig build
installs each Windows target as the exact pair `opentui.dll` and `opentui.pdb`.
The wrapper requires that pair, selects only `opentui.dll`, and copies it into
candidate evidence as `libopentui.dll`; the PDB is never designated or packaged
as a candidate. Because stripped PE images need not retain a COFF symbol table,
the wrapper reads Windows exports from the PE export directory with the
runner-pinned `llvm-readobj --coff-exports`; ELF and Mach-O continue to use
`llvm-nm --defined-only --extern-only`.

The macOS query suffixes are part of the build input, not a post-build label.
Zig 0.14.1 accepts both queries, and the resulting Mach-O load commands must
still be inspected for the recorded 15.0 floor.

The wrapper invokes targets individually because the pinned upstream
all-target build logs and continues after a target failure. An individual
nonzero exit is therefore an unambiguous hard failure.

## Artifact verification

Both copies are verified independently before their hashes are compared:

- exactly one expected library exists per target and no unexpected executable
  output is accepted;
- LLVM inspection reports the expected ELF, Mach-O, or PE/COFF format and the
  expected x86-64 or arm64 machine;
- every symbol in `requiredOpenTuiNativeSymbolNames` is an exact defined
  external export after normalization;
- the pinned normalization policy is regression-tested and was adopted only
  after the exact runner preserved the external export listing, format, and
  architecture for both retained Linux artifacts and the retained macOS x64
  artifact while removing its `N_SO` and `N_OSO` build/cache paths;
- both macOS artifacts declare minimum macOS `15.0`, with no lower deployment
  target accepted;
- printable-string scans reject either build root, either cache/output root,
  the workspace, `/Users/`, `/home/`, `/root/`, temporary-root markers,
  Windows drive build paths, debug-source suffixes, and other unreviewed
  absolute paths; platform loader paths are handled by a narrow documented
  allowlist, including Mach-O's exact `/usr/lib/dyld` and
  `/usr/lib/libSystem.B.dylib` load-command values;
- the host-compatible macOS arm64 candidate loads through
  `OPENTUI_LIBRARY_PATH`, reports ABI version `2`, and passes Noir's headless
  health check without terminal control bytes;
- a temporary package snapshot overlays the matched candidates and a generated
  candidate-only manifest, then passes manifest integrity and the packaged
  health check without modifying the workspace; and
- the tracked manifest and all six tracked libraries still pass the existing
  verify-only check unchanged.

Static validation of the five non-host targets does not claim runtime testing
on those platforms. Six-platform packaged execution remains a later release
gate. Likewise, the two-root comparison proves path- and order-independence
within one recorded runner image and host; it does not claim cross-machine
reproducibility. An independent rebuild on a different host remains an
optional later verification before beta or stable adoption of these bytes.

## Evidence and provenance

Each successful run writes a self-contained evidence directory containing:

- an immutable run ID and UTC start/end timestamps;
- Noir commit/tree, recipe commit and aggregate recipe digest;
- OpenTUI commit/tree and clean-status checks before and after both builds;
- runner base, configuration, and archive digests plus the resolved package
  inventory;
- Docker client/server, Zig, LLVM, Dart, host, and runner versions;
- official tool input URLs and checksums, the `zg` URL and Zig package hash;
- exact argv arrays, environment values, mounts, target order, and exit codes;
- raw and normalized SHA-256 tables for root A and root B;
- format, architecture, export, deployment-floor, ABI, path, manifest, and
  health-check reports;
- protected-path hashes proving that the ABI contract, generated bindings,
  gitlink, manifest, and tracked native artifacts did not change; and
- a statement listing every matched candidate as a SHA-256 subject.

The provenance statement uses the SLSA v1 predicate shape and records external
parameters, resolved dependencies, builder identity, commands, and run
details. It is explicitly labelled local and unsigned: this phase does not
claim a hosted build service, non-forgeable attestation, or a SLSA level.
Publishing or attaching provenance is a later separately authorized action.

The build result is accepted only when both SHA tables contain the same six
hashes and the evidence directory itself receives a sorted inventory and
SHA-256. Failed runs retain logs and a failure statement but never emit a
matched-candidate designation.

Because `.context/` is workspace-local and gitignored, a successful run must
be preserved before any approval request: mirror the evidence directory, the
runner-archive checksum record, the matched candidate bytes, and the existing
Phase 1 recovery artifacts to a reviewed directory outside every Conductor
workspace, the default being `~/noir-release-recovery/`, and re-verify every
mirrored file's SHA-256 against its recorded value. The mirror's absolute
path and verification results are recorded in the later tracked
evidence-summary commit.

## Tests and review gates

Before the first native build, focused tests must demonstrate that the wrapper:

- plans exactly the six approved targets and reverses only root B's order;
- requires the explicit execution flag and a clean, correctly pinned fixture;
- constructs networkless, non-TTY, read-only-source container commands with
  isolated paths and caches;
- rejects missing, extra, path-leaking, wrongly formatted, wrong-architecture,
  export-incomplete, floor-incompatible, or nonidentical fixture artifacts;
- refuses unsafe cleanup targets and any tracked-artifact destination; and
- produces stable, complete build information and provenance from injected
  deterministic inputs.

The focused tests are run RED before implementation, then green. An independent
reviewer inspects the contract, implementation, tests, command transcript,
evidence, and full diff. Focused checks, architecture tests, the ordinary suite
excluding `restricted-process-lifecycle`, tracked manifest verification, and
`git diff --check` must pass before a coherent slice is committed and pushed.

## Mandatory stop conditions

Stop without replacing or publishing anything when:

- an input, pin, recipe, runner, or tool digest differs from its reviewed
  value or fails signature verification;
- a source or workspace cleanliness check fails;
- a build needs an OpenTUI edit, gitlink advance, ABI/header/generated-binding
  change, or an unreviewed normalization step;
- any target fails, produces unexpected output, leaks a path, fails static or
  host health checks, or differs between roots;
- the macOS floor is not exactly compatible with the recorded `15.0` policy;
- the evidence cannot account for every command, input, and output; or
- completing the next step would alter `native/`, `native_manifest.json`, a
  recovery URL, remote state, visibility, Actions, a tag, a release, or
  publication state.

A successful Phase 2 build ends with verified candidate bytes and preserved
local evidence only. The agent must then present both SHA-256 tables and the
evidence inventory for the release owner's direct review and request the
separate native-artifact replacement approval required by the release plan.
The owner authors that approval after inspecting the evidence; the agent does
not draft approval text for pasting.
