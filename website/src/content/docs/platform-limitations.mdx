# Platform support and limitations

Noir is an alpha prerelease, not a stable 1.0 release. Check the target OS,
architecture, terminal features, and current limitations before distributing an
application.

<PrereleaseNotice>
  Source can be ahead of the latest package on pub.dev, and open release gates
  are not implied complete by this website.
</PrereleaseNotice>

## Supported targets

| Platform          | Architectures | Current boundary              |
| ----------------- | ------------- | ----------------------------- |
| macOS             | x64, arm64    | macOS 13.0 or later           |
| Linux             | x64, arm64    | glibc 2.17 or later           |
| Windows           | x64, arm64    | Desktop terminal applications |
| Android, iOS, web | —             | Not supported                 |

Run the packaged health check on the machine that will run the application:

```sh
dart run noir:health_check
```

The command verifies native-asset resolution and a headless buffer/render
lifecycle. It does not open a real terminal, read raw input, or prove escape
rendering.

On macOS, Dart 3.10 native-asset hooks can build with a macOS 12 target even
though Noir’s bundled OpenTUI libraries require macOS 13. A build can therefore
succeed on macOS 12 and fail later when the native library loads.

## Account for terminal capabilities

Some output crosses a protocol negotiated with the user’s terminal or
multiplexer. Noir can generate or request the behavior; the receiving terminal
still decides whether it works.

| Feature                 | Noir behavior                                                        | External dependency                             |
| ----------------------- | -------------------------------------------------------------------- | ----------------------------------------------- |
| Terminal images         | Chooses Kitty, Sixel, or block fallback through `ImageProtocol.auto` | Terminal and multiplexer protocol support       |
| OSC52 clipboard         | Emits copy requests for explicit document selection                  | Terminal, tmux, or Screen acceptance and policy |
| Enhanced keyboard input | Can request Kitty keyboard reporting                                 | Terminal support and encoding                   |
| Mouse input             | Enables reporting when requested by `runTuiApp`                      | Terminal reporting and a real input session     |
| Color and links         | Records 24-bit color and semantic hyperlinks                         | Terminal rendering support                      |

Headless tests and Noir Driver are useful for layout, paint cells, cursor state,
and parsed input. They cannot replace a real-terminal check for these protocol
boundaries.

## Known user-visible limits

<dl className="limitation-list">
  <div>
    <dt>Leading zero-width text</dt>
    <dd>
      A text run that begins with a zero-width grapheme can differ between
      Noir’s source-correct layout and the pinned native paint path. Avoid
      isolating a leading zero-width grapheme into its own styled run.
    </dd>
  </div>
  <div>
    <dt>Border clipping</dt>
    <dd>
      A decorated box that straddles a clipped viewport edge can paint its full
      border outside the native scissor rectangle. Keep bordered regions inside
      the viewport when exact clipping matters.
    </dd>
  </div>
  <div>
    <dt>macOS terminal teardown</dt>
    <dd>
      On an observed iTerm path, alternate-screen teardown can restore the
      launch cursor imperfectly. Always dispose <code>TuiApp</code>; skipping
      cleanup does not avoid the limitation and leaves terminal modes owned.
    </dd>
  </div>
  <div>
    <dt>Linux native-library metadata</dt>
    <dd>
      The official Linux libraries retain absolute build and debug paths from
      OpenTUI’s release environment. They are upstream artifact metadata, not
      paths produced on the application’s machine.
    </dd>
  </div>
  <div>
    <dt>Fractional opacity on ordinary text</dt>
    <dd>
      The pinned native text fast path does not apply opacity values between
      <code>0.0</code> and <code>1.0</code>; ordinary text paints as fully
      opaque. A value of <code>0.0</code> remains transparent. Alpha blending is
      available on supported cell and rectangle paint paths, but the native
      stack alone cannot implement a general <code>Opacity</code> widget.
    </dd>
  </div>
  <div>
    <dt>Forced Kitty graphics through tmux (alpha.3)</dt>
    <dd>
      This combination is unsupported because initial image placement can
      overlap existing content until a resize. Use{' '}
      <code>ImageProtocol.auto</code>
      under tmux; it selects block rendering.
    </dd>
  </div>
  <div>
    <dt>Hot reload</dt>
    <dd>
      Reload does not rerun <code>main()</code> or <code>initState()</code>.
      Live stack signatures, enum-to-class changes, and native library changes
      can require a full restart. See
      <a href="/docs/getting-started#change-the-running-app">Getting started</a>
      for the development-runner loop.
    </dd>
  </div>
  <div>
    <dt>Drive mode</dt>
    <dd>
      <code>NOIR_DRIVE=1</code> is headless. It is not evidence of raw-mode or
      terminal-protocol behavior. See
      <a href="/docs/testing">Testing</a> for where Driver fits.
    </dd>
  </div>
  <div>
    <dt>Native error detail</dt>
    <dd>
      Some low-level native failures cannot be reported precisely to Dart. Keep
      application recovery at the supported widget or hosting boundary where
      possible.
    </dd>
  </div>
</dl>

The pinned OpenTUI source and bundled native libraries are framework-owned.
Applications should not rebuild, replace, or patch those artifacts as part of a
normal installation.
